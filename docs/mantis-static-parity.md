# 文档分析范围与 Mantis 静态审计复用验收

本次调整依据产品讨论：典型项目上传一份设计文档，通常不超过一百页；切片只在必要时使用。漏洞检查需要完整承接 Mantis 的静态审计方法和执行逻辑。本文件区分当前接入状态、静态产品适配，以及接入前的历史差距；运行接入通过不代表真实模型效果已验收。

## 最新代码接入状态

已替换自编代码审计链：`mantis_engine.py` 连接产品数据，`mantis_worker.py` 在独立进程中直接调用固定版本的 `main.pipeline()` 和 `core.graph_loader`。建模阶段使用原图前四个节点，漏洞阶段使用原生静态子图的 12 个节点，保留调查、去重、复核和挑错的判定分支；明确移除 reproducer、repro_classifier、patcher 三个动态相关节点。critic_classifier 的 viable 分支直接进入静态 chainer，chainer 完成后进入 calibrator。后者使用 Mantis 原生 auto 范围选择、Surveyor、调查规划、反馈、去重、复核、挑错、校准与覆盖账本。原生研究节点加载完整 Skill；没有子 Agent 工具时使用原技能允许的顺序执行路径。

全部顶层技能及引用资料随引擎打包，活跃角色完整技能进入指令，校准的完整 27 项规则同时加载。静态环境注册表和兼容工厂限定为只读静态模式，所有节点不注册 run_sandbox、run_sandbox_with_evidence 和 apply_patch 工具；其余上游核心源文件保持原样。离线语法加载、字面指令绑定、全局预算、读取记录、阶段接口与输出映射属于适配层。来源与摘要保存在 `vendor/mantis/SOURCE.json`，运行快照同时固定原始来源及适配代码摘要。

需求实现检查通过原生工具查询符号、调用方、被调用方、函数边界和代码模型。原生评分和原始发现状态保留，不由展示层重新计算。原始数据库、阶段图、会话、复核判定和关联结果保存到该运行的 Mantis 工作目录。同项目先前成功运行的原生知识库可作为历史继承，当前模型与源码仍重新检查；这不等于已实现增量扫描。

文档调度已取消固定每 20 块分组，默认一个整体分析任务，材料超出配置的读取预算才分组，并保留全部块库存。原始解析块仍用于来源引用。

## 接入决策：直接采用 Mantis 代码审计机制

代码理解、代码威胁建模、调查规划、按需切片、漏洞研究、去重、复核、挑错和风险校准由嵌入本项目的 Mantis 审计子系统负责。保留上游核心代码、工作流、工具和技能的来源关系，不再把当前自编的同名角色链作为最终实现，也不重新设计切片或漏洞判定算法。Mantis 默认图与完整技能方案中未接通的能力，按已核对的上游实现接入，不把文本声明当运行能力。

我们开发文档到安全需求的上游、需求实现检查、项目管理和四个输出物的界面。两个分析子系统共用 Python、ADK、模型网关、项目快照、运行控制和预算边界；不形成两套模型接入框架。只对 Mantis 增加必要的接口适配，适配项必须有独立记录。

接入边界如下：

1. 输入适配器向 Mantis 提供固定代码快照、设计背景和安全需求引用。设计声明与代码事实分别标识；需求缺口可成为调查线索，但不能成为漏洞已成立的依据，也不能替代独立攻击面调查。
2. Mantis 按自己的调查与发现流程执行。项目的需求检查复用其代码模型与只读导航能力，但独立维护每条需求的落实结论；Mantis 的漏洞筛选不能删除安全需求或将需求标为已实现。
3. 输出适配器保存原始威胁、发现、复核理由、风险与调查覆盖，再映射到四个产品输出物。不能在映射中把未知转成已确认、把静态结果转成动态验证，或重算一套自定义漏洞评级来替代上游结果。
4. 调度适配负责运行标识、暂停恢复与累计预算；路径、状态提交和受控工具保留可验证的边界。上游的应用入口、云平台配置及文件存储接口可以适配，审计逻辑不因此简化。

旧代码审计 Skill 保留作迁移来源和测试兼容；生产工作流使用文档与需求的五个自定义角色，以及两个 Mantis 原生阶段入口。下面的接入前差距表用于核对迁移缘由。

## 文档默认整份分析

一份文档作为一个完整设计输入，先识别系统、资产、角色、模块、数据流和边界，再生成安全需求。正文、表格仍保存为可定位的解析块；解析块是读取和引用单位，不自动变成独立分析任务。

是否拆分由完整技能、材料、工具往返、已有产物和输出预留的实际上下文预算决定，不能仅凭页数或固定块数决定。一百页不保证能在一次模型调用中完整处理；可以在同一个分析任务中分段读取，累计核对阅读范围。

仅当预计超限、读取额度不足或确有独立分析范围时，按章节、模块或业务数据流拆分。拆分任务共享全局设计背景，完成后必须检查跨章节关系、冲突、重复要求和跨模块控制。没有读到的内容保留未完成状态；摘要不能替代缺失原文的检查。标准映射按条款、需求检查按需求组织任务并在内部逐项检查验收条件，属于领域工作划分，与文档切片分开。

接入前按每 20 个文档块创建任务的固定策略，已替换为按材料大小判断是否需要拆分。

## 漏洞检查的完整复用范围

产品继续只有四个阶段：安全需求、威胁建模、需求实现情况、漏洞。漏洞阶段内部保留完整调查链，不因为界面只有一个阶段而压缩审计步骤。

目标数据流为：固定快照与历史背景 → 结构导航与系统模型 → 威胁和调查库存 → 初筛 → 初筛驱动的深挖及补充调查 → 同根因去重 → 独立复核 → 攻击条件挑战 → 静态结论 → 跨发现关联与静态攻击链分析 → 风险校准 → 调查经验与报告。没有候选时跳过发现处理，但仍核对调查库存和未完成范围。

调查以安全问题、入口、数据流和不变量为单位。代码切片仅帮助组织注意力，不能封闭源码读取权限，也不能把调用方、被调用方或公共保护机制切断。小仓库默认整体调查；大仓库可使用 Mantis Surveyor 排序，但未入热点的范围保留在待查库存中。

## 静态产品的明确适配

沿用已确定的不运行目标程序边界：动态复现、再攻击、自动补丁及补丁验证不进入当前产品。原图依赖复现成功才到达的攻击链环节，改为基于源码和前置条件的静态分析，并明确未动态验证。静态链不会继承动态确认状态。原生成功完成后提交状态的回调从已移除的复现节点转到静态 chainer；只有 reviewer 确认且 critic 判断成立的分支能到达，原生终态拒绝保护继续有效。底层 StaticOnlyEnvironment 只用于固定快照的文件读取和兼容上下文，不提供实际目标执行。

需求缺失与可利用漏洞分开判定。漏洞侧保留 Mantis 的规则及评级方法；上游漏洞筛选中排除安全卫生、部分纵深控制或资源耗尽的政策不能删除独立需求检查中的已适用需求。静态执行模式下，缺少运行环境不能直接判定误报。必要的静态边界适配必须列出差异，不能宣称逐字原样复用。

## 完成门槛

每行迁移项必须有可定位的运行入口、实际传递的输入输出、失败或未知分支，以及有预期结论的行为验证。特别验证：公共鉴权使候选不成立、跨文件危险调用成立、相似位置但根因不同、初筛阴性不能覆盖未深查范围、部署条件未知、读取截断、跨模块攻击链，以及预算耗尽后保留调查库存。

检查清单逐项通过后，才可以称为完整复用 Mantis 的静态审计逻辑。现有契约测试通过、12 个角色存在和技能文本完整加载，都不能单独证明这一点；真实 DeepSeek 的分析效果仍需另行验证。
