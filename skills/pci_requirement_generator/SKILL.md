# 结构化标准兼容需求生成手册

## 质量目标与执行顺序

必须同时使用完整加载的共享方法 `_shared/security-requirements.md`。它给出 OWASP 风险到具体控制的适用前提、验收行为、反例和排除边界。按本角色职责执行，不把风险类别或通用口号当作需求，不把指导资料当成项目证据或正式合规条款。

本技能的质量由实际安全需要的合理性、业务边界内的覆盖、最小充分控制和可核验行为决定。references/quality-method.md 与 references/cases.md 随正文完整加载，必须执行；先做其中的专业调查与正反例检查，再按正文接口提交。来源精确、字段齐全和记录数量都不能证明分析正确。质量调查不新增未声明字段，调查清单保存在现有 summary，具体问题保存在 gaps/rationale。

## 明确使用场景

这是历史结构化标准路径的兼容角色。当前预计算标准流程是“独立准备固定控制和向量 → 项目 mapper 选控制 → 服务原样绑定”，不会调用本角色重新生成控制。不要因为技能文件存在，就在项目过程中生成第二套控制或向量。

本角色实际输入为 scope.clause_ids、对应规范原文、必要父级范围、相关设计事实与已有 applicability。输出为 StageOutput 中的 Requirement，origin=PCI_DSS。它不输出 StandardControl、controls.jsonl 或向量，不承担 prepare-standard 的程序执行。离线控制目录采用另一文件契约，不能把该契约的 localizations、source_excerpt 等字段混入此工具提交。

## [METHOD] 从规范义务到可检查行为

### [PCI_REQUIREMENT_GENERATOR-01] 核对目标库存和进入条件

列出全部 scope.clause_ids；读取每条规范正文和适用上下文。只处理当前库存，不因检索扩展而随意增补规范编号。确认已有匹配为技术相关或条件相关且属于代码责任；纯非代码、无关或明确不适用义务不能重新生成产品需求。

已有 status=UNDETERMINED 的代码相关候选可以形成保留前提的控制需求。不得替前阶段认定正式 PCI 范围、改成 APPLICABLE，或输出已合规结论。输入没有设计关联或责任依据时，先读取已有事实及原文；仍不明确就写具体 gap，不为完成条款数量硬造模块。

### [PCI_REQUIREMENT_GENERATOR-02] 分解规范句的义务结构

对每条规范逐句标出：义务主体、保护对象、动作、约束、强度、条件、例外、时序和参数。强制值仅来自该规范义务，示例和指导中的值不能升级成要求。

分开阅读 defined approach、applicability notes、testing procedures、guidance 及父级范围。前两类决定义务和边界；后两类用于理解及审计方式。不能把“访谈人员是否了解策略”变成“代码提供人员访谈接口”。

一条规范可能有几个独立行为：建立机制、限制访问、保护记录、实际运营。先列出各行为，判断谁承担，然后只保留与目标子系统有关的控制。不能因为条款含技术名词就把整条组织责任都分配给代码。

### [PCI_REQUIREMENT_GENERATOR-03] 建立可观察的条件化要求

对每个保留行为写出明确目标模块、主体、对象、操作与约束。statement 保存规范适用条件；验收项描述相应允许、拒绝、限制、失效或外部落实事实。不同安全目的拆成不同需求，重复表述合并来源。

采用“最弱满足实现”试验：只检查一个接口有日志是否足以满足规范的特定操作记录义务？只检查密码字段存在是否足以满足其保护要求？若不够，验收项必须说明所保护的具体行为和范围；不能用“符合 PCI DSS”替代逐项判断。

已有设计需求只用于识别同义控制和目标责任，不替代规范来源。规范与设计冲突时仍忠实表达规范条件，并在 rationale/gaps 说明冲突；不要降低规范以适配当前设计。

### [PCI_REQUIREMENT_GENERATOR-04] 分别安排代码机制和部署责任

| 责任 | 需求处理 | 后续检查边界 |
| --- | --- | --- |
| 代码机制，如授权范围或无效配置拒绝 | 保留可定位行为与拒绝条件 | 原始源码可以支持或反证 |
| 相关实际部署，如生产启用或日志实际留存 | 保留具体对象、前提和实际要求 | 源码不能证明实际落实，可为 NOT_CODE_VERIFIABLE |
| 与子系统无关的组织、人员或物理义务 | 不生成本次产品代码需求，说明范围原因 | 不制造代码实现任务 |
| 缺少相关性或责任材料 | 写明需要的事实 | 不伪造代码义务 |

一个规范有两种责任时拆开验收对象，不能因部署未知而跳过能静态检查的机制。无法通过代码验证不等于规范无关、控制不存在或存在漏洞。

### [PCI_REQUIREMENT_GENERATOR-05] 原文反查和库存结算

对生成要求逐条反查：规范直接支持该行为吗？例外和限定词是否仍在？目标是否属于本子系统？验收项是否混入测试程序？存在外部事实时是否分项？是否改写了正式适用性？

所有目标条款要有真实控制要求或具体缺口；如果接口或存储校验要求每项候选产生结果而材料不足，保留未完成/失败状态，不用空泛要求骗过库存检查。不要补造规范页码、数据分类、实际部署或认证结论。

## 真实提交协议

最终只提交工具声明的 Requirement 字段：标题、模块、statement、acceptance_criteria、rationale、实际来源和条件。旧任务单条规范的 task_owned_requirement_provenance_v1 协议可能由程序固定 origin 与 clause_ids；以当前工具声明为准，允许省略时省略，不提交冲突的归属。

任何标准目录字段都不能出现在 Requirement 中；程序也不会从散文中再推理生成控制。来源只引用本次实际读取的规范及必要设计依据。通过 set_model_response 一次提交全部目标结果，不在提交后补总结或调用模型修补。

## 完成条件与禁区

规范和影响义务的适用说明全部读完；目标库存已结算；每项是独立可检查行为；参数、例外和范围有真实来源；与组织整体的责任分开；最终字段与当前工具 Schema 一致。

禁止在预计算项目阶段调度本角色替代控制绑定，禁止向量化标准，禁止混用两种输出契约。references/cases.md 展示规范拆解、审计动作排除与兼容接口边界。
