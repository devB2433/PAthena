# pci_requirement_generator

本技能用于安全需求与纯静态代码分析。方法参考 google/mantis 的 mantis-plan，已按本项目证据、模块和合规边界改写。

## [SNAPSHOT]
只分析任务固定的快照，所有证据通过登记 ID 读取；旧快照事实不能直接证明当前情况。

## [EVIDENCE]
肯定结论必须引用原始文档、标准或代码证据；上游摘要仅是调查线索。

## [UNKNOWN]
缺证、解析失败、索引不完整和运行环境未知必须保留；不能判为安全、误报或不适用。

## [BOUNDARY]
识别模块、子系统、入口、数据流、主体与信任边界；检查跨模块关系及公共控制。

## [INVENTORY]
任务 scope 的条款、验收项或调查目标全部产生结果或明确缺口；检索相关性不能删除库存。

## [STATIC]
仅静态分析，不执行程序，不宣称动态复现、补丁验证或通过合规认证。

## [OUTPUT]
输出 StageOutput；不属于角色的记录不得生成；引用既有对象的确切 ID；无结论时保留 gaps。

## [PCI_REQUIREMENT_GENERATOR-01]
只处理 scope.clause_ids 中相关或条件相关且 control_scope=CODE_RELATED 的候选条款。逐条读取结构化原文及必要父级上下文；即使正式适用性 status 为 UNDETERMINED，也生成保留适用条件的代码相关控制需求。不得将候选写成已确定适用或已合规，不重新改写前一阶段的正式适用性判断。

## [PCI_REQUIREMENT_GENERATOR-02]
只提交 requirement 记录，origin 必须为 PCI_DSS，clause_ids 使用目标条款精确 ID；每条目标条款形成相关控制需求并引用规范原文，不引用库存外条款。只提取与目标子系统相关的规范性控制，不复制整条标准的全部组织义务。statement 保留适用前提；不要把“确认适用范围”“访谈管理员”“观察流程”“检查合规证明”等测试动作当作验收项。其他设计需求只提供简要索引用于去重，不作为新的规范来源。

## [PCI_REQUIREMENT_GENERATOR-03]
每条需求说明目标模块、必须满足的安全行为、适用条件和可逐项检查的验收条件；区分规范性要求、指导和测试程序，不把示例写成统一强制阈值。独立安全行为分开成项，重复描述合并原始来源。

## [PCI_REQUIREMENT_GENERATOR-04]
与当前子系统直接相关的部署配置和运行控制仍保留真实安全需求，例如要求实际启用认证审计；后续检查应标为 NOT_CODE_VERIFIABLE（无法通过代码验证）并说明依赖的配置或材料。纯组织流程、人员责任、访谈和现场观察不单独生成代码相关需求；不要将标准评估方法转成产品必须实现的功能。

## [PCI_REQUIREMENT_GENERATOR-05]
上下游需求只作定位线索，所有新需求必须以原始标准和设计依据为基础。原文冲突、版本限制、条件和缺证写明，不补造项目部署、实现或认证结论。

## [METHOD] 独立标准控制准备与兼容边界

本技能描述标准控制整理方法，同时保留旧结构化标准接口的提交契约。当前预计算工作流不调度本角色：项目 mapper 选择已保存控制后，由程序直接绑定。本角色不能在项目检索时再次生成控制、向量化标准或修改已有模板。

### 规范提取

逐条读取规范义务、适用说明及必要父级范围。测试程序仅描述如何核验，指导用于解释，不作为规范来源。source_excerpt 应锚定确切规范原文，来源页码属于实际条款；不得引用标准编号之外的材料作为该条款义务。

将条款拆成可独立判断的控制，分别明确保护对象、主体、动作、条件、例外和验收行为。不能将标准示例变成统一强制阈值，也不能遗漏条件否定词。一个条款可以形成多个控制，但重复安全行为不应重复计数。

### 验证方式分类

- TECHNICAL / CODE：能够通过程序行为、配置校验或接口控制调查的机制。
- DEPLOYMENT / DEPLOYMENT：规范要求实际部署或运营事实，如生产启用、实际保留或运行流程。保留真实要求，不把静态分析不足说成漏洞。
- ORGANIZATIONAL / NON_CODE：人员、组织、物理和其他非代码义务。保留在完整标准库，但不自动绑定到当前产品代码。

同条款有多种责任时拆分控制，不能因为包含一个技术词就将全部组织义务分配给代码。代码机制与部署事实可分别形成控制。

### 双语与固定版本

中英文版本具有相同的控制 ID、规范来源、适用条件与验收项库存，译文不得增加或删除规范义务。每种语言直接保存相应需求文本。控制版本固定后由 prepare-standard 校验并预计算，项目运行不改写。

在旧接口兼容调用中仅提交当次工具声明允许的 Requirement 字段、精确条款 ID、规范来源与条件；独立控制目录的交付则遵从 StandardControl 文件 Schema。两种容器的字段不能混用。准备完成前校验全条款库存、控制 ID 唯一性、来源原文、页码、分类与双语一致性；遗漏或无法判断的条款记录明确缺口，不伪装为完整目录。
