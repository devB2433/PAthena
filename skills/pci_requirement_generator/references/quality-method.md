# 兼容规范转控制的质量调查

## [PCI_REQUIREMENT_GENERATOR-06] 义务原子化以保护结果为单位

先区分主体、保护对象、强制行为、适用前提、合法例外和责任归属。一个条款里的代码机制、部署事实、组织制度、审计员测试动作分别标出；只有本子系统实际承担的相关义务进入 Requirement。不要按每句话机械拆一条，也不要把不同保护目的并成‘符合标准’。

保护结果与实现方式分开。规范要求指定算法/参数时忠实保留；规范仅要求保护时，不能自行加入固定产品和未经要求的值。若 source_excerpt 不含例外，继续阅读父级/适用说明，不以摘录完整代替规范上下文完整。

## [PCI_REQUIREMENT_GENERATOR-07] 用双向控制库存判断完备

对 scope 中每个目标条款建立“规范原子义务 → 代码/部署/组织责任 → 生成需求 ID 或排除理由”。从每条需求回查真实义务，排除指导性建议和测试程序；从每个相关义务回查需求，找遗漏。summary 保存简要清单；gaps 精确说明缺失范围事实，不用通用‘需确认’掩盖未读条款。

依赖实际部署的真实相关义务保留验证方式，不改写成源代码已证明。组织培训、人员访谈、物理门禁若与本代码责任无关，应排除而不是生成永远无法实现的代码需求。已有设计不够强时仍表达规范原义，不能降格来配合项目现状。

## [PCI_REQUIREMENT_GENERATOR-08] 用正反实例检验控制边界

合成规范：“系统应记录特权操作并保护记录不被未经授权修改；运营方按适用策略留存；审计人员访谈运营负责人。”

应分别表达：特权操作的可归属记录机制、记录完整性保护、相关实际留存责任。若产品提供日志接口而留存由外部平台承担，说明两者责任，不要求应用自行构建整个日志平台。访谈属于审计程序，不是产品需求；没有固定天数就不能填一年。

合成规范：“适用于存储的认证秘密，公开标识符不在本义务范围。”只有 JTI 的项目不能因 token 一词获得秘密加密存储义务。存储真实 bearer token 且范围条件成立时，必须保留秘密保护；不能因为代码扫描无法确认整个 PCI 环境就判定技术无关。

## [PCI_REQUIREMENT_GENERATOR-09] 不混淆离线目录与项目兼容任务

本技能改进并不会使它自动成为预计算目录生成器。当前项目预计算路径继续原样绑定已保存控制；本角色只服务明确调度的历史兼容任务。不得重做标准向量化、改写冻结目录、伪造控制 ID 或声称已重建本机标准库。需要更新固定目录时应走独立、带版本和来源的准备流程。

## [PCI_REQUIREMENT_GENERATOR-10] 保留规范强度与合法拒绝

规范规定‘仅授权访问’是访问的必要条件，不生成‘授权就必须成功返回’；保留有效生命周期、业务和状态拒绝。规范约束外部披露/可用性效果时，不添加禁止内部临时写入、立即物理销毁或某一代码顺序的要求，除非原文确实规定。新增工程方案应明确不是规范原义，本兼容角色不能借拆控制为规范扩大义务。
