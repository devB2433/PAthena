# 兼容生成的规范拆解与接口边界

以下规范均为合成示例。正式调用只能使用任务提供的真实规范，不照抄示例控制。

## 案例 A：一句规范含多个责任

示例要求“限制指定信息的读取，并在实际部署中记录相关操作”。

先拆行为：读取范围限制、记录机制、实际启用责任。确认哪些属于本子系统。不同安全目的可形成独立需求；代码日志机制和实际生产启用不要混为无法区分的验收。

每个 Requirement 都由真实规范支持，保留限定对象与条件。不能从这句话生成固定产品、额外算法或全组织培训义务。

## 案例 B：审计程序不能成为产品功能

测试说明要求访谈管理人员并观察配置。规范本身要求配置受到限制。

生成的产品需求约束配置访问行为；访谈和观察不是 acceptance_criteria。若实际配置生效依赖环境，可保留外部落实要求，后续无法通过代码验证。不能生成“系统必须提供访谈证明 API”。

## 案例 C：正式范围未知，技术责任清楚

前序匹配明确控制与当前认证子系统有关，但未确定正式标准范围。

允许生成带 applicability_conditions 的 PCI_DSS 来源要求，rationale 说明条件性关联，不能将适用性更改为已正式适用或把缺失范围事实写成代码必须实现的行为。标准原文是规范来源，设计仅用于目标关联。

## 案例 D：与子系统无关的义务

条款要求物理访问程序，设计和代码只涉及令牌验证，没有相关设备控制职责。

不能为了覆盖条款给令牌模块创建物理门禁要求。说明责任与对象不同。如果当前 scope 本不该包含它，记录上游范围问题；不要伪造技术需求使任务通过库存校验。

## 案例 E：禁止两种容器混写

当前 set_model_response 要求 Requirement，不能加入 StandardControl 的 localizations、source_excerpt、source_pages 或 control_type。输出 origin/clause_ids 是否由任务拥有，以当次工具声明为准。

当前预计算项目运行只应由 mapper 选择、服务绑定；这个兼容技能没有“生成固定目录”或“重新向量化”的能力。prepare-standard 校验已有 controls.jsonl 并预计算向量，不从本角色散文推理控制。不要宣称在项目阶段完成了新标准控制目录。

## 完成核对

条款 ID 精确，引用是规范原文，条件与例外完整，产品义务与审计程序分开，每个安全行为可逐项判断。材料不足时保留未完成或具体缺口，不把“符合规范”当作替代需求。
