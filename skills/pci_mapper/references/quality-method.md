# 控制匹配的合理性与召回调查

## [PCI_MAPPER-09] 用义务交集判断关联，避免关键词套标准

对当前需求先写出“保护对象—主体—行为—风险—责任”，对每个固定控制独立写相同五项。解释两者交集和差集：同叫日志，但业务调试日志不自动对应支付访问审计；同叫 token，但随机任务 ID、公开审计标识符与可用于认证的秘密不是同一种对象。不得为了匹配强行改变项目资产分类。

一个控制可能比设计需求更强。这不代表必须排除：若规范的实际数据、主体和责任前提成立，可选择完整固定控制并保留条件；不能把固定文本裁剪成设计已承诺的子集。反之，只有主题相似而对象不成立时应排除，不把 POTENTIALLY_RELEVANT 当作无理由兜底桶。

## [PCI_MAPPER-10] 对召回不足与过匹配做相反调查

从每个实际安全行为规划有限的互补查询：行为本身；对象别名/双语术语；失效机制。合并命中再读正文和父级适用范围。发现条款包含另一种直接相关责任时扩展；查询只换大小写不算新覆盖。相似度和重排仅决定阅读顺序，不能证明精度或召回。

对空结果进行一次机制/对象别名复查并说明查询边界；不要把空匹配当成无合规需求。对大量结果按具体责任收敛；不要因为召回了整章就全选。没有证据证明非代码责任属于本子系统时，不能生成代码任务来填补标准覆盖率。

summary 保存“本需求行为 → 已查询主题 → 所选控制 ID/排除理由 → 尚缺范围事实”。未读候选不计已评估，未检索标准部分不计已覆盖。项目仅查询既有向量与固定控制，不重新生成控制、标准向量或规范义务。

## [PCI_MAPPER-11] 分开不相关、条件相关和源码外落实

支付报表导出涉及被确认的账户数据：访问授权、导出副本保护可能相关；员工入职培训、机房访客登记与代码无关，排除。设计未说明是否有持卡人数据：不能宣称正式适用，也不能靠‘未提支付’宣布正式不适用；先看该行为的技术关联，保留具体范围条件。

实际日志保留时间属于部署落实，但日志正是本子系统产生且标准前提成立时，它可以技术相关；不能因为静态无法验证而排除。标准要求‘存储时保护某类秘密’而设计只含公开 JTI，则不能仅凭 token 字样绑定秘密存储控制。

## [PCI_MAPPER-12] 最终质量反查

逐个所选 ID 问：如果工程师原样实现这条控制，是否在本系统实际承担的行为上产生保护？有没有把供应商/组织责任转嫁？若不选，会遗漏哪项真实义务？结论分别写入现有 relevance、control_scope、status 和 rationale，不合并三轴。同义需求复用控制标识但不篡改固定目录；控制是否实现由后续检查决定。

## [PCI_MAPPER-13] 匹配约束而非无条件结果

匹配授权控制时保持它与到期、取消、业务拒绝的交集，不把规范许可变成服务必须成功的保证。设计描述当前不使用某危险操作，不足以关联该操作的所有标准控制；先证明真实保护对象和路径。规范明确要求的内部机制与项目推导方案分别说明，不将项目新方案假称固定目录原义。
