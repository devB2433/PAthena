# requirement_reviewer

本技能用于安全需求与纯静态代码分析。方法参考 google/mantis 的 mantis-review，已按本项目证据、模块和合规边界改写。

## [SNAPSHOT]
只分析任务固定的快照，所有证据通过登记 ID 读取；旧快照事实不能直接证明当前情况。

## [EVIDENCE]
肯定结论必须引用原始文档、标准或代码证据；上游摘要仅是调查线索。

## [UNKNOWN]
缺证、解析失败、索引不完整和运行环境未知必须保留；不能判为安全、误报或不适用。

## [BOUNDARY]
识别模块、子系统、入口、数据流、主体与信任边界；检查跨模块关系及公共控制。

## [INVENTORY]
任务 scope 的条款、验收项或调查目标全部产生结果或明确缺口；检索相关性不能删除库存。

## [STATIC]
仅静态分析，不执行程序，不宣称动态复现、补丁验证或通过合规认证。

## [OUTPUT]
输出 StageOutput；不属于角色的记录不得生成；引用既有对象的确切 ID；无结论时保留 gaps。

## [REQUIREMENT_REVIEWER-01]
逐条复核既有需求对象，返回带 subject_id 的 review，不另造需求替代原记录。

## [REQUIREMENT_REVIEWER-02]
独立读取原始文档和标准，不能只相信生成角色的理由。

## [REQUIREMENT_REVIEWER-03]
检查来源、条件、范围、冲突、重复、验收可执行性和条款关系。

## [REQUIREMENT_REVIEWER-04]
检查需求是否覆盖批量操作、旁路接口与跨模块保护。

## [REQUIREMENT_REVIEWER-05]
SUPPORTED 表示需求依据和表达得到支持，不能表示实现已经通过。

## [REQUIREMENT_REVIEWER-06]
缺证用 NEEDS_EVIDENCE；真实错误用 REJECTED 并给出原始反证。

## [REQUIREMENT_REVIEWER-07]
重点检查条件是否被丢失、示例取值是否被强制化、显式/推导来源是否混淆、版本和 TODO 是否被误当作最终设计、验收项能否逐条核对。peer 需求摘要用于发现重复，目标需求仍必须独立读取原文。复核不修改原始需求；审查原子性失败或存在不支持的强制条件时明确说明，不默默生成替代项。

合规控制必须与目标代码子系统有关；无关组织义务、访谈或现场观察等审计动作不能作为代码验收项。实际部署或运营才能验证的相关安全需求仍然有效，不因源码无法证明就否定需求；检查时应标为 NOT_CODE_VERIFIABLE。确认代码机制与实际部署行为分项描述，合规范围条件留在需求前提中。

## [METHOD] 独立复核流程

### 调查输入

只复核 scope.subject_ids 指定的需求。读取需求的完整 statement、验收项、origin、适用条件、来源与关联控制；上游 rationale 不能代替原文。根据来源逐段重读设计和标准，保留原需求 ID，不生成替代版本。

### 逐项审查

每项需求至少检查下列问题，并将实际检查的规则 ID 写入 checked_rules。

| 审查面 | 支持条件 | 应当挑战的问题 |
| --- | --- | --- |
| 来源真实性 | 引用原文确实说明该安全行为，或推导有明确设计风险依据 | 引文只是示例、TODO、愿景，或者取值被强制化 |
| 来源分类 | EXPLICIT_DESIGN、INFERRED_SECURITY、PCI_DSS 与依据一致 | 将推导称为原文要求，或未匹配却声明标准归属 |
| 条件与范围 | 主体、对象、模块、启用条件、例外和版本被保留 | 丢失限定词，或将整个组织义务分配给当前模块 |
| 原子性 | 一个可独立判断的控制，验收项能够分别检查 | 一条吞并多个无关控制，或多个同义验收项重复计数 |
| 可检查性 | 能说明允许、拒绝、限制、状态变化或外部验证责任 | 仅写“安全”“合理”“符合标准” |
| 跨路径覆盖 | 需求范围包含设计中的批量、异步、管理、旁路和公共控制 | 把某条局部路径当作完整业务范围 |
| 标准控制 | 规范义务、适用条件和保存控制一致 | 用指导、测试程序代替规范要求，或改写固定控制模板 |
| 重复与冲突 | 与其他需求的差异可由对象、条件或行为解释 | 重复、互相矛盾，或静默选择某一设计版本 |

同模块不意味着重复；共用安全词汇不意味着同一控制。peer 摘要用于找线索，判断目标需求仍必须引用其原文。对标准绑定的需求，检查保存的控制内容和适用前提，不能自行修改验收项后宣布修复。

### 判定门槛

- SUPPORTED：来源、分类、范围和表达有依据，验收项能够检查；这只是需求复核结论，不是实现通过。
- NEEDS_EVIDENCE：关键材料缺失、条件无法确定或原文解析不足。列明具体缺少什么及其如何影响判断。
- REJECTED：原文反证足以证明要求被误述、错误归属或超出设计范围。引用反证，说明哪一项错误；不能因当前代码尚未实现或需要外部验证而否定需求。

提交前核对每个目标 subject_id 恰有复核结果，checked_rules 是实际执行的规则，原需求及其关联保持不变。摘要分别说明有依据的需求、真实错误和材料不足，不补造第二套需求清单。
