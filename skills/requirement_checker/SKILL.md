# requirement_checker

本技能用于安全需求与纯静态代码分析。方法参考 google/mantis 的 mantis-researcher，已按本项目证据、模块和合规边界改写。

## [SNAPSHOT]
只分析任务固定的快照，所有证据通过登记 ID 读取；旧快照事实不能直接证明当前情况。

## [EVIDENCE]
肯定结论必须引用原始文档、标准或代码证据；上游摘要仅是调查线索。

## [UNKNOWN]
缺证、解析失败、索引不完整和运行环境未知必须保留；不能判为安全、误报或不适用。

## [BOUNDARY]
识别模块、子系统、入口、数据流、主体与信任边界；检查跨模块关系及公共控制。

## [INVENTORY]
任务 scope 的条款、验收项或调查目标全部产生结果或明确缺口；检索相关性不能删除库存。

## [STATIC]
仅静态分析，不执行程序，不宣称动态复现、补丁验证或通过合规认证。

## [OUTPUT]
输出 StageOutput；不属于角色的记录不得生成；引用既有对象的确切 ID；无结论时保留 gaps。

## [REQUIREMENT_CHECKER-01]
本任务只检查 scope 中的唯一 requirement_id。所有 assessment 必须使用该确切 ID，按 acceptance_criteria 逐项返回且每项仅一次，保持验收条件原文。不得检查或创建其他需求，也不能用另一条需求的同名验收项替代。

## [REQUIREMENT_CHECKER-02]
设计覆盖与代码实现状态分开；文档说启用不能证明代码已实现。

## [REQUIREMENT_CHECKER-03]
从入口沿服务、公共中间件、数据层和配置寻找保护及反证。

## [REQUIREMENT_CHECKER-04]
缺少局部检查不证明控制缺失，先找共享控制或外部责任。

## [REQUIREMENT_CHECKER-05]
STATIC_SUPPORTED 需要覆盖目标入口的原始静态证据；词法检索无结果不能证明缺失。

## [REQUIREMENT_CHECKER-06]
确认代码控制违反生成 IMPLEMENTATION_GAP；明确设计冲突生成 DESIGN_GAP；代码调用链、共享控制或检查覆盖不足使用 UNKNOWN 并说明已查范围和缺口。已确认存在、但依赖实际部署、运营记录或发布文档的安全要求使用 NOT_CODE_VERIFIABLE（无法通过代码验证），说明为何源码不足以证明。不能因为无法通过代码验证就生成缺陷。本任务生成的 finding 必须令 requirement_ids 等于 [scope.requirement_id]，保持需求与缺陷的关联。

## [REQUIREMENT_CHECKER-08]
上游已自动排除与当前代码范围无关的合规控制。status=UNDETERMINED 或带 applicability_conditions 的需求不能变成“已正式适用”或“已合规”。适用范围是需求的前提，不是产品代码的验收项。根据代码逐项检查相关控制的实际行为；代码机制与实际部署要求分开判断：代码检查有依据则给出对应静态状态，只有实际部署或运营部分使用 NOT_CODE_VERIFIABLE。范围未知不替代代码检查，也不因仓库没有部署材料就判为代码漏洞。不要再输出 EXTERNAL_EVIDENCE_REQUIRED。

## [REQUIREMENT_CHECKER-07]
source_inventory 表示本次快照实际提供的材料数量。存在代码时，不得仅凭设计文本或一次检索无结果就声称“快照只有文档”。先通过 get_mantis_model 获取模块线索，再使用 find_symbol、代码文件路径或函数名检索原始实现；search_evidence 同时匹配源码内容与位置，指定 source_type="code" 可排除文档。沿目标入口、配置校验、共享控制与错误处理读取代码后才能判断。优先批量读取相关块，并继续读取工具返回的 remaining_ids；检索结果与来源清单只提供位置，未读取的材料不得引用。充分搜索仍缺少相关实现时，明确已查范围并保留 UNKNOWN。

## [METHOD] 逐需求静态落实检查

### 1. 固定验收库存和安全不变量

只处理本任务的 requirement_id。逐字读取 statement、全部验收项、来源、适用条件和已绑定控制的 verification_method。将每个验收项对应到“何种主体、何种对象、何种操作、何种条件下，必须允许、拒绝或限制什么行为”。这是调查工作表，不改写需求或验收项。

重新读取设计与规范原文，区分代码应实现的机制和实际部署、运营行为。缺少正式合规范围的事实不能替代代码调查，也不能把有条件需求提升成无条件合规义务。

### 2. 先定位，再读取原始实现

get_mantis_model 只用于获得模块和入口线索。结合源码路径、路由、函数名、配置项与安全行为进行词法搜索，再使用 find_symbol 定位定义、get_function_boundary 读取完整函数、find_callers/find_callees 跟踪调用关系。继续分页并调查所有歧义候选，结构索引不完整或无结果时继续词法搜索。

搜索摘要、模型描述和历史结论不是源码证据。必须实际读取将要引用的源码块，优先使用批量读取并完成 remaining_ids。不会因为索引没有返回调用方，就声称路径不可达或控制不存在。

### 3. 沿保护对象建立调查路径

从入口追踪到敏感操作：主体建立、对象解析、控制决策、数据访问、结果返回。随后反向寻找共享中间件、服务层、数据访问层、框架配置和外部责任。检查条件、执行顺序、作用域、默认值和失败处理；“有一个鉴权函数”不证明目标入口调用了它。

按需求范围检查单条、批量、异步、回调、管理、导出与其他旁路入口。读取关键调用方和被调用方，不只引用危险行。对配置控制区分代码默认值、可配置开关、拒绝无效配置的机制以及实际部署是否启用。只有最后一项需要实际环境，不应掩盖其余代码机制的调查。

### 4. 主动找支持和反证

对每个验收项同时寻找满足路径和可能绕过路径。确认攻击者能控制的输入、权限起点、对象范围和前提；检查更早的保护、公共过滤、错误返回和安全默认。文档声称有控制、函数名看似校验、库通常安全或缺少局部检查都不足以单独定论。

常见调查方向如下，只有与当前需求相关时才使用。

| 需求控制 | 重点核对的实现行为 |
| --- | --- |
| 身份与会话 | 令牌或会话检查是否覆盖入口；身份撤销或变更如何影响后续访问；失败是否拒绝 |
| 授权与租户隔离 | 操作与对象是否同时检查；查询及写入是否限制实际主体；批量和后台任务是否旁路 |
| 输入与外部调用 | 输入到敏感操作的实际数据流；编码、校验、白名单与执行位置；回调、重定向和解析差异 |
| 数据与密钥保护 | 库调用、密钥来源、访问控制、序列化、日志及导出路径；代码行为与环境配置分别调查 |
| 状态与完整性 | 重复、并发、回退、错误路径是否保持所要求的不变量 |
| 审计与资源限制 | 相关操作是否真正产生记录或受到限制；代码机制与实际保留、告警配置分别判断 |

### 5. 每个验收项独立作出判断

| 状态 | 所需依据 |
| --- | --- |
| STATIC_SUPPORTED | 当前源码中可解释的机制覆盖验收对象和调查到的相关路径；说明入口、决策和执行位置，以及静态范围限制 |
| PARTIAL | 有真实实现支持，但存在已查明未覆盖的对象、路径或条件；说明满足与未满足部分 |
| VIOLATED | 实际源码行为与验收要求冲突，有具体可到达路径或反证；不能仅凭关键词搜索无结果判断缺失 |
| UNKNOWN | 调用关系、共享控制、外部依赖或调查覆盖不足，尚不能支持或否定；列明已查范围与缺口 |
| NOT_CODE_VERIFIABLE | 要求本身有依据，但验收依赖真实部署或运营状态；说明需要的材料，不能自动生成缺陷 |

静态支持不证明所有部署都启用了控制。不同验收项可有不同状态，不能用其中一个失败或成功覆盖整条需求。design_status 与 implementation_status 分别判断；不能把“设计有声明”当成代码支持。

### 6. 缺陷与最终提交

只有有实际源码反证的控制违反才能形成 IMPLEMENTATION_GAP；明确设计冲突才能形成 DESIGN_GAP。需求缺口不是已确认可利用漏洞，后续代码风险审计仍负责调查攻击前提与影响。UNKNOWN、NOT_CODE_VERIFIABLE 或范围未知不能为了补全报告而生成 finding。

核对验收项库存：原文完全一致、每项恰好一次、没有其他需求的验收项。肯定实现状态及代码违反均引用当次实际读取的原始源码。使用任务声明的来源句柄与记录 ID 前缀；任务关联遵从工具 Schema 中的固定关系，不能挪用另一需求 ID。提交允许的 assessment 与 finding 列表，保留明确缺口；不凭散文代替结构化提交。
