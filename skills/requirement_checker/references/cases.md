# 实现检查轨迹与判定案例

案例代码和行为均为合成教学材料，不是被扫描项目；正式结果只能引用实际读取的源码。

## 案例 A：公共控制能解释局部缺失

验收：受保护订单查询必须限制到当前主体的授权范围。

入口函数直接调用服务，没有局部权限 if。调查不能到此停止：

1. 读路由注册和中间件，确认该入口是否受主体建立和授权包装。
2. 读服务调用与查询构造，确认过滤器使用可信主体范围而不是请求中可改的 tenant_id。
3. 词法搜索所有相关调用点，合并索引调用方；读批量、导出、管理和异步调用。
4. 读拒绝和异常分支，确认失败不会继续敏感查询或返回完整结果。

若这些代码证明控制覆盖当前验收范围，可为 STATIC_SUPPORTED。只读到安全中间件定义、但不知道路由是否使用，应为 UNKNOWN；不能支持，也不能认定控制缺失。

rationale 需包含真实路径、控制绑定的对象、实际拒绝行为和调查过的旁路。代码引用不能只包含中间件函数名。

## 案例 B：异步任务中的可信主体丢失

材料说明任务应限制发起者范围。代码在提交时检查主体，但任务负载中的客户字段由请求提供；工作器用服务凭证按该字段读数据，没有看到绑定检查。

继续读任务构造、可信字段赋值、消息入口、工作器查询及公共封装。如果代码明确允许发起者影响范围且路径没有保护，该静态反证可支持 VIOLATED 和 IMPLEMENTATION_GAP。必须说明攻击前提和数据流，不能只说“工作器没鉴权”。

若任务负载校验由仓库未提供的外部服务承担，调用契约也不明确，则控制链有缺口，应为 UNKNOWN。不能凭记忆认定队列消息可信，也不能仅凭服务账号判定漏洞。

## 案例 C：有一条安全路径不意味着所有路径安全

单条读取过滤租户，批量导出直接按用户输入列表查询。要阅读完整批量入口与共享查询层，再判是否存在实际绕过。

明确违反路径成立时优先 VIOLATED，不用 PARTIAL 弱化真实冲突。PARTIAL 仅表达已证明的局部落实及明确范围限制，必须说明未落实的具体部分；单纯尚未调查另一入口是 UNKNOWN。

一项原子验收不能因为另外的验收已经支持而被改成支持。每项独立作判断。

## 案例 D：代码机制与生产状态

验收一要求无效安全配置被拒绝，验收二要求生产启用该配置。

读配置解析、默认值、校验调用与异常处理。验收一可以据代码支持或反证；验收二没有实际部署材料，应为 NOT_CODE_VERIFIABLE，说明需要的事实。不要让验收二的外部依赖影响验收一的调查。

如果代码明确允许无效值而继续执行，第一项可以 VIOLATED；不能把整个需求都标成 NOT_CODE_VERIFIABLE。若设计只推荐某配置而需求写成强制，描述来源问题，不私自修改验收标准。

## 案例 E：增量源码与索引不完整

只有一个处理函数，没有路由注册、公共鉴权或库实现。词法搜索只覆盖已登记材料，空索引表示缺索引或无已索引调用，不表示完整仓库没有控制。

片段里的明确数据泄露分支可以作为反证，但“没有 if”不能证明不存在上游鉴权。需要外部调用关系才能判断时 UNKNOWN，列出缺少哪些路径。不要为了强行得到结论要求运行系统。

## 案例 F：设计沉默与设计冲突

需求依据为有效推导，设计没有描述保护：design_status 可以 MISSING，这本身不能生成 DESIGN_GAP Finding。若设计明确要求“未经授权用户也能读取受保护对象”，且与当前需求成立条件确实冲突，才形成明确设计缺口，引用双方来源。

不要以“文档没写”和“代码搜不到”相乘得到设计和实现均违反。

## 案例 G：撤销、缓存和时序

读取令牌验证、缓存键、有效期判定、撤销写入及入口调用。确认缓存命中分支是否跳过必须的失效判定，撤销何时影响验证。代码有撤销接口但所有入口使用独立静态令牌校验，不能证明验收支持。

文档明确允许的传播延迟是判定条件；不造一个更严格的即时失效标准。缺外部缓存一致性语义时说明哪条结论仍未知，不编造动态复现结果。

## 输出骨架

每项 rationale 说明：原验收 → 原始入口和关键调用 → 控制/反证与范围 → 已排除替代解释 → 判定及剩余条件。

evidence_ids 和 counter_evidence_ids 不是数量指标；引用要能让读者复查关键条件、输入来源和敏感操作。未知不是漏洞；静态支持也不是全系统安全保证。
