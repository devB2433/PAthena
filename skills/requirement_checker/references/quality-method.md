# 验收语义与静态路径的完整对应

## [REQUIREMENT_CHECKER-09] 将需求变成反例查询，不变成关键词查询

逐项冻结验收原文，在内部列出“受保护动作—主体来源—对象范围—必要时序/状态—失败应阻止什么”。再构造一条最小违反路径作为调查目标：登录用户替换对象 ID、工作器用更强服务身份取数、已取消任务继续发布、旁路直接下载结果。只能使用设计/代码实际存在的前提；不能因需求涉及授权就凭空假设多租户。

支持判断必须回答这条反例被哪段真实控制阻断，而不是哪个函数名字像安全检查。违反判断必须给出可达路径和冲突行为，而不是“没有找到某关键词”。需求合理性仍由复核负责；即使输入有疑义也不得自行降低验收项或给另一条需求打分。

## [REQUIREMENT_CHECKER-10] 按风险机制选择深入调查方法

| 控制目的 | 必须追踪 | 常见伪支持和伪违反 |
| --- | --- | --- |
| 对象/租户授权 | 输入对象→查询/修改条件→授权主体→敏感操作；追踪批量每个元素 | 登录中间件不是对象授权；service 层统一过滤可能排除局部缺 if 的误报 |
| 异步代办 | 创建授权→可信消息来源→任务对象/发起者绑定→执行范围→结果读取 | worker 有服务凭证不证明越权，也不证明保留用户范围 |
| 撤销/取消/并发 | 状态写入→可见性/缓存→检查与操作顺序→竞争窗口/原子约束 | 存在 cancelled 字段不证明阻止发布；数据库条件更新可能提供约束 |
| 凭证与声明 | 可信签发/验证→来源绑定→用途/受众/对象限制→生命周期 | 有 Node 信息不等于 Node 绑定；公开标识符不等于 bearer secret |
| 日志/数据副本 | 敏感字段到记录/输出的流向→实际读者→脱敏/权限 | 有 logger 不证明审计完整；源码无法证明生产实际保留期 |
| 参数到危险操作 | 数据转换→最终解释点/目标限制→异常分支 | 类型校验不自动阻止注入；安全库调用仍需确认参数语义 |

索引不完整时合并词法与调用线索；追踪到真实控制或具体不可见边界。不能以文件数多、读取行数多或调用次数多替代调查结论。

## [REQUIREMENT_CHECKER-11] 结算路径覆盖而非给全局安全背书

每个验收项的 rationale 说明已查入口、共享控制、关键分支、合法例外、未见材料。若该项只约束单一入口，不强制审查无关系统；若声称保护所有入口，不能只检查样本。peer 的通过结论不是本项代码依据。

代码支持机制但部署值未知时，代码命题可 STATIC_SUPPORTED，独立部署命题 NOT_CODE_VERIFIABLE。若一个未拆开的验收项同时要求机制和实际生效而无法完整核验，不给整体 STATIC_SUPPORTED：指出具体无法通过代码验证的外部事实，按实际已证行为和状态定义判定；不能将“未知”包装成 PARTIAL。

确认代码冲突前，寻找能阻断路径的更早授权、共享服务约束、数据库行级过滤和事务条件；找到后验证目标确实经过。调用目标、框架注册或外部库语义不可见时说明 UNKNOWN，不虚构实现。

## [REQUIREMENT_CHECKER-12] 两个对照案例

A：handler 仅检查登录，随后 service 的查询使用由认证主体生成的 tenant_id，忽略请求里的 tenant_id，且所有导出入口都调用此 service。不能仅因 handler 没有租户 if 就报违反；必须核实查询绑定与调用覆盖后判断。

B：worker 从队列取用户传入的账单 ID，以服务账号直接读取；创建入口的鉴权仅判断用户登录，没有对象授权，下载也仅靠顺序任务 ID。若这些实际代码均已读，可分别证明异步对象授权、结果读取控制的违反。不要合成一个没有引用路径的‘可能越权’，也不要为每个文件重复报告同一根因。

C：配置声明保留日志 365 天。源码可以证明选项默认值和校验，不能证明生产实际留存。相关需求仍成立，实际运营命题标记 NOT_CODE_VERIFIABLE；不要生成“没有部署日志就是漏洞”。

## [REQUIREMENT_CHECKER-13] 正例路径也受其他真实约束

授权通过但任务到期、取消或尚未完成，代码合法拒绝不自动构成授权控制违反；若输入验收真的无条件要求返回，保留输入缺陷与实际冲突，不偷偷改成较弱验收。取消检查可由原子发布条件实现，不要求代码一定先有一个独立 if；后台写私有临时文件不是已发布，标记过期不等于物理删除。核查实际可达的读取/发布效果和共享约束，避免把内部步骤不同当作不满足。
