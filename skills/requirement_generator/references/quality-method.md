# 需求的合理性与完备度调查

## [REQUIREMENT_GENERATOR-10] 先判断是不是安全需求

每条候选先完成五个判断，rationale 用简明因果链保留结果：

1. **保护必要性**：保护哪个实际资产或权限？哪种设计允许的输入/状态变化会破坏它？只有功能描述、内部函数接线、常规指标或项目进度，不能因为出现在安全设计里就列为安全需求。
2. **事实充分性**：设计已确认哪些攻击前提？缺的是控制本身，还是连资产/权限边界也未知？前者可推导 INFERRED_SECURITY，后者写具体 gap 或带实际前提的条件化要求。不能因原文没有写控制而禁止所有推导。
3. **最小充分约束**：要求保护结果而不指定无依据的产品、算法、角色或数值。考虑不同可行实现；如果存在更弱约束同样阻止已识别失效，就缩小要求。
4. **合法业务可行性**：写出一个应允许的正常/管理员/恢复场景。要求若阻断它，先修正范围或例外，不以更严格为更安全。
5. **责任与可核验性**：控制由哪个子系统承担？代码机制和生产事实分别是什么？外部真实要求保留并说明验证方式；与本子系统无关的组织义务不生成产品需求。

对 EXPLICIT_DESIGN 也做必要性筛选：忠实摘录不自动等于安全需求。若它是维持安全兼容、撤销、授权或审计目的的行为，说明安全后果再保留。若只是开发实现步骤或普通功能，用事实承接，不强行变成需求。

## [REQUIREMENT_GENERATOR-11] 从业务失效反推最小控制，允许有根据的新增需求

按“已知设计前提 → 可行失效路径 → 被破坏的不变量 → 最小控制 → 验收反例”推导，而不是把标准目录全部套上。引文支持的是设计前提，不必包含尚未写出的控制句；source.modality=INFERRED，origin=INFERRED_SECURITY，rationale 明确推导链及剩余假设。不要将推导标为原文承诺，也不要伪造 source_polarity 来证明规范句存在。

例：客户各自拥有私有账单，用户可指定账单 ID，后台用服务账号取数。即使原文没写鉴权，也足以推导“后台取数不得超出发起者被授权的账单范围”。这不是凭空增加业务。若结果文件可通过下载入口获得，还必须调查下载对象授权；创建时鉴权不能覆盖新增读取边界。若文档明确结果是经业务授权的公开发布物，则不得一律要求下载登录。

不要用所有权直接推导“只能本租户”；有被委托管理员时最小要求是“在明确授权范围内”，包括合法委托。不要从“秘密需保密”直接规定 AES 型号、固定保留期或永不记录可公开审计标识符。

## [REQUIREMENT_GENERATOR-12] 以设计行为库存做覆盖结算

生成前，沿原文的每个真实敏感流程建立内部表：

| 项目 | 要回答什么 |
| --- | --- |
| 保护对象和动作 | 哪个资产/权限在什么动作中暴露？ |
| 入口与边界 | 谁能影响它？身份、所有权或信任在哪里变化？ |
| 状态和旁路 | 创建、执行、获取结果、修改、撤销、失败、重试中哪些实际存在？ |
| 控制结算 | 已有哪条需求覆盖；合并到哪条同义需求；为什么无需额外控制；或缺少什么事实？ |

双向回查：从每个需求返回实际流程，排除无场景要求；从每个敏感动作返回控制，找遗漏。不能因同主题已有“认证”就跳过对象授权、服务代办授权与结果读取；也不能给每个接口重复生成同一不变量。设计未涉及的流程不得为了填表制造需求。

summary 必须给出“流程/边界 → 本批需求 ID（或不新增的具体理由）”的简短覆盖清单，并说明剩余 gap。它是本次分析存档，不用自造顶层字段。不要用需求条数、引用条数或通用清单项数宣称完备。

## [REQUIREMENT_GENERATOR-13] 用两个相反实例检验每条控制

每个控制至少在内部验证一对实例：一个应当拒绝的违反路径，一个必须保持可用的合法路径。验收项表达保护结果、关键条件和失败行为，不能只写函数存在。

“任务创建须登录”在用户选择别人的账单时仍满足，保护不足；“永远禁止跨客户读取”阻断授权管理员，约束过强。合理控制是对具体对象和动作做有效授权，并在异步服务身份下保持该范围。是否每次重新鉴权由设计的权限时效约定决定；没有约定不要发明立即撤销或固定延迟。

当原文只说可用指标 OR 审计观察，保留择一而非强制两种。可选功能约束只在启用时成立。信息性 Node claim 不是直接 Node 绑定；停发新 token、验证旧 token、记录旧标识符分别分析。需求内部的验收项不能互相推翻。

## [REQUIREMENT_GENERATOR-14] 停止规则和已知反例

提交前再次查找：敏感副本读取、异步服务身份、合法特权例外、生命周期与回退、未覆盖边界。能从已读事实明确推导的控制应在本次生成中补齐；无法确认的关系写 gap，不把所有缺失保护都推给未来人工确认。不得设最低需求数、固定推导比例或“所有维度各一条”的配额。

保留：基于私有对象与非可信选择器的对象授权；基于服务身份代办的范围传递；基于真实高成本入口的资源约束；原文要求的撤销行为。
排除：测试覆盖率阈值；每个函数都必须加密；未涉及支付却强加 PAN 控制；把 Non-Goal 写成禁止行为；无依据指定唯一组件可读状态；把公开 JTI 当作必须隐藏的完整 bearer token。

覆盖清单只表示本次已读设计范围的调查闭合，不证明未知业务、完整标准或所有漏洞都已覆盖。

## [REQUIREMENT_GENERATOR-15] 最后执行强制义务收敛

先删去仅重述安全无关功能/不存在危险解释点的候选；这些留在 Fact。某输入当前只用作显示，不足以生成禁止它参与所有路径、URL、对象键或查询的永久义务。若存在真实浏览器输出边界，可依据具体注入风险推导输出约束，但不能假造该输入到 SQL/文件系统的路径。

将“只有授权时才允许访问”与“只要授权就必须返回结果”分开。授权是必要条件；对象不存在、未完成、已取消、已过期、业务拒绝仍可合法阻止访问。正例验收应写“不得仅因合法委托/跨客户而拒绝，其他业务和生命周期条件仍适用”，不写无条件‘授权管理员必须取得文件’。至少把每条正例与其他需求的撤销、到期和失败规则比一次。

原文规定取消后不得发布，不等于禁止生成尚未公开的临时文件，也不等于必须物理删除。约束最终保护效果，不无依据收紧到特定内部顺序；可行的原子条件更新、事务、发布门控等方案均应允许。

正文或任一验收项新增了实质保护机制，不能因安全目标在原文出现就全部标 EXPLICIT_DESIGN。若新增机制与原义务属于同一控制，整条标 INFERRED_SECURITY，明确哪些是原文前提、哪些是推导；若有独立控制目的则拆分。每个 source 的 modality 也按该项实际依据填写，不能把推导的准入、权限或失败行为标成原文 REQUIRED。
