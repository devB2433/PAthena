# requirement_generator

本技能用于安全需求与纯静态代码分析。方法参考 google/mantis 的 mantis-threat-model，已按本项目证据、模块和合规边界改写。

## [SNAPSHOT]
只分析任务固定的快照，所有证据通过登记 ID 读取；旧快照事实不能直接证明当前情况。

## [EVIDENCE]
肯定结论必须引用原始文档、标准或代码证据；上游摘要仅是调查线索。

## [UNKNOWN]
缺证、解析失败、索引不完整和运行环境未知必须保留；不能判为安全、误报或不适用。

## [BOUNDARY]
识别模块、子系统、入口、数据流、主体与信任边界；检查跨模块关系及公共控制。

## [INVENTORY]
任务 scope 的条款、验收项或调查目标全部产生结果或明确缺口；检索相关性不能删除库存。

## [STATIC]
仅静态分析，不执行程序，不宣称动态复现、补丁验证或通过合规认证。

## [OUTPUT]
输出 StageOutput；不属于角色的记录不得生成；引用既有对象的确切 ID；无结论时保留 gaps。

## [REQUIREMENT_GENERATOR-01]
先整理显式需求，再依据业务资产、攻击者和数据流推导安全要求。

## [REQUIREMENT_GENERATOR-02]
每条需求明确目标模块、应满足行为、来源、推导理由和至少一个可验收条件。

## [REQUIREMENT_GENERATOR-03]
区分设计原文要求和推导要求；此角色不虚构 PCI DSS 条款映射。

## [REQUIREMENT_GENERATOR-04]
不读取代码来删除未实现的要求；未实现的控制仍保留。

## [REQUIREMENT_GENERATOR-05]
组件内与跨模块、跨子系统要求都要分析；覆盖认证、授权、数据保护和可用性相关范围。

## [REQUIREMENT_GENERATOR-06]
需求应是原子且可检查的安全行为，保留触发条件、对象、范围与拒绝/错误行为；不得把整套认证流程合为一条，也不得把一般功能、发布清单和贡献流程直接当作安全需求。同一控制的重复描述合并来源，不同控制不可因为同一模块而合并。

## [REQUIREMENT_GENERATOR-07]
原文示例中的 issuer、域名、audience、24 小时等取值不自动变为项目强制要求。显式需求按文档表述保留；补充控制标为 INFERRED_SECURITY 并说明风险和假设，不能伪称原文已要求。可选控制的条件必须同时出现在 statement 和 acceptance_criteria 中；不能要求所有场景开启可选的映射或自定义规则。

## [REQUIREMENT_GENERATOR-08]
TODO、未来工作、阶段性设计、互相冲突的声明必须保留为 gaps 或有条件需求，不替项目做设计决策。验收项说明可观察的允许、拒绝、回退或限制行为，避免“符合标准”“安全”“合理”这类无法核对的表达。本角色只产生需求，不宣称已实现。

与目标子系统相关、但需要部署或运营才能落实的真实安全要求仍保留，明确对象与前提，后续可标记“无法通过代码验证”。不要将访谈、现场观察、合规范围确认等审计动作作为产品代码的验收要求；代码机制与实际部署行为拆成独立验收项。

## [METHOD] 从设计事实形成可检查需求

### 1. 回到原始设计，建立候选库存

上游 Fact 只是定位线索。读取涉及的原文、完整表格条件和相关章节，分别记录明确要求与风险推导候选。不要把“采用某框架”“存在用户角色”“通过 HTTPS”直接转换成覆盖所有路径的安全保证。只处理本次设计范围，不读取代码后降低需求标准。

对每个业务资产和信任边界，逐个询问：谁可以做什么、作用于谁的对象、何时允许、何时拒绝、失败时如何处理、是否存在跨租户或跨用户影响。保留对象、主体、操作、条件、约束和来源之间的关系。

### 2. 用威胁检验候选的必要性

沿文档描述的数据流审视攻击者能控制的输入和敏感动作。下表是调查方向，不是要为所有项目机械生成同一套要求。

| 方向 | 需要问清的行为 |
| --- | --- |
| 身份与会话 | 哪个入口必须识别主体？会话、令牌、撤销、身份变更和服务身份的条件是什么？ |
| 授权与隔离 | 主体能对哪些对象做哪些操作？单条、批量、异步任务与管理接口是否采用相同范围？ |
| 输入与外部调用 | 哪些输入影响查询、路径、命令、回调、外部地址或反序列化？边界处应限制什么？ |
| 数据与密钥 | 需要保护哪些具体数据？传输、存储、日志、导出、销毁与密钥访问如何限制？ |
| 完整性与状态 | 重放、并发、重复提交、状态转换、失败回退会不会绕过业务安全不变量？ |
| 可用性与追溯 | 哪类攻击会消耗关键资源？哪些敏感操作应有可归属的审计记录？ |

推导要求必须写明设计对象、攻击或失效场景与保护目的，标为 INFERRED_SECURITY。不能以“行业最佳实践”代替具体风险依据，也不能为凑覆盖率补充与业务无关的要求。正式标准编号由后续 mapper 绑定，本角色不生成 PCI DSS 归属。

### 3. 写成原子控制与验收条件

一条需求表达一个可独立判断的安全控制。statement 包含触发条件、主体、对象和要求的行为。验收项分别描述可观察的允许、拒绝、限制、失效或回退行为；不能只写“安全”“符合标准”“正确校验”。避免把同一描述拆成多个同义验收项，也不能把不同控制合并成无法逐项判断的一条大需求。

保留示例和强制要求的区别：示例地址、算法、超时时长不自动变成必须值。可选功能的要求在 statement 和验收项中同时带上启用条件。对未定设计记录 gaps 或条件需求，不替项目选择最终策略。

### 4. 区分代码机制和外部落实

代码能判断的机制与依赖部署或运营的要求分别描述。例如日志接口是否有访问控制，与生产日志是否按要求保留，是不同验收对象。真实外部控制仍可形成需求，但不把访谈、观察、合规范围确认等审计动作变成代码必须实现的功能。

### 5. 去重、反查与提交

按“控制对象 + 安全行为 + 条件”比较候选；同义描述合并来源，条件不同或控制不同保留。逐条反查原文是否支持 EXPLICIT_DESIGN，推导依据是否足以支持 INFERRED_SECURITY。检查每条需求的模块、来源、验收项、假设与推导理由是否齐全。只提交需求与缺口，不判断实现状态，不改写前一阶段的设计事实。
