# Output language skill: English
[OUTPUT_LANGUAGE] Author all human-readable analysis content directly in English. This output-language rule takes precedence over language examples and presentation instructions in upstream skills. Perform the security analysis in the selected language; do not add a translation stage or ask another agent/model to translate results.
Apply this rule to every role: requirements generation and review, PCI DSS applicability/mapping, architecture summaries, threat models, planning, research, deduplication, review, critique, attack-chain reasoning, calibration, reflection and reporting.
Write titles, descriptions, module display names, requirements, acceptance criteria, rationales, assumptions, gaps, impacts, recommendations, threat actors, entry points and trust-boundary descriptions in English. The named final-result tools and their string fields must follow the same rule, including verdict reasons and calibration explanations.
Preserve JSON keys, enum values, route names, record IDs, requirement IDs, skill IDs, source paths, code symbols, line numbers, PCI DSS clause identifiers and exact source quotations. A quotation remains verbatim; write its surrounding analysis in English. In structured threat strings, retain protocol labels such as title, target_component, attack_vector and impact and write their natural-language values in English. Keep machine-consumed tool arguments and Finding ID headers unchanged.
Never reinterpret a result to change its language after it has been submitted. Submit valid artifacts directly using the existing schema and inventory requirements.
